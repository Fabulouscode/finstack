# ADR 0026: Fees

- **Status:** Accepted
- **Date:** 2026-09-26

## Context

Fintech businesses earn from fees: a percentage on collections, a flat charge per withdrawal, negotiated rates for large merchants. Prices change often and differ per customer, so they can't be constants in code. Every fee charged must also be explainable later: which price applied, and where the money went.

FinStack provides the mechanism and sets no prices of its own.

## Decision

### Rules

A fee rule (`fee_rules`) applies to an **operation** (`payment`, `payout`, `transfer`) in a **currency**, either as the platform default or for one **organization**:

```
fee = fixed + ceil(amount × bps / 10 000), then held within [min, max]
```

- Exact integer arithmetic. The percentage rounds **up** to the minor unit.
- An organization's own rule wins over the default. With no rule, there's no fee.
- **Rules are never edited.** Setting a rule supersedes the active one for its scope (it gets `superseded_at`), under an advisory lock per scope. Retiring a rule ends it without a replacement. Both are audited, and the audit entry records which rule was replaced.
- Each transaction stores `fee_amount`, `fee_currency` and `fee_rule_id`, so every fee can be traced to the rule that priced it.

### Who pays, and when

| Operation | Fee | Ledger |
| --- | --- | --- |
| Payment | **Taken from the credit** (the merchant pays, like Stripe or Paystack), on what the wallet receives after conversion, in the wallet's currency | Credit to the wallet, then wallet → `fee-revenue`, in the same database transaction; from *pending* under a settlement hold |
| Transfer | **Added on top**, paid by the sender; the recipient gets the full amount | Transfer, then sender → `fee-revenue`; fails as a whole if amount + fee isn't available |
| Payout | **Added on top**; held with the amount | Success: reserved → clearing (amount) and reserved → `fee-revenue` (fee). Failure: both released. Bank reversal: amount returned **and fee refunded** |

- **Locked at the start.** A payment's fee is fixed when it's created, like its FX quote, so rule changes don't alter payments already in flight. A payment whose fee would consume the whole amount is refused (`AMOUNT_TOO_SMALL`).
- **Refunds don't return the original payment fee** (the industry norm). The refund debits the wallet by the refunded amount.
- Fees post to a `system:fee-revenue:<CURRENCY>` account as their own ledger transactions (`fee:…` references). Revenue per currency shows in the admin overview next to FX revenue.

### API

- `GET /v1/fees/quote` and `GET /v1/organizations/:id/fees/quote` (the organization's own rates; API keys allowed) let apps show the cost before the user confirms.
- `GET` / `POST /v1/admin/fee-rules` and `POST …/:id/retire` for admins.
- Payments, payouts and transactions show `fee: { amount, currency }`. A transfer recipient doesn't see the sender's fee.

## Consequences

- Tiered or volume-based pricing (for example "1% above $10,000 a month") isn't modelled. It would be another rule type evaluated in `FeesService`.
- A late FX re-quote keeps the fee locked at the start (capped at what was credited).
- The FX spread (ADR 0009) stays a separate charge, priced by `FX_SPREAD_BPS`.
