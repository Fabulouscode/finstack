# Deploying FinStack

This guide takes FinStack from your machine to a server: first as a **sandbox** (production settings, test money), then **live**.

## What you are deploying

| Component | Requirement | Notes |
|---|---|---|
| **API** | The Docker image built from `Dockerfile` (Node 24) | Stateless; run as many instances as you need. |
| **Workers** | The same image with `WORKERS_ENABLED=true` | Outbox relay, webhook processing, payouts, settlement releases, reconciliation, outbound webhooks and email. |
| **PostgreSQL** | Version 17 | The source of truth. The ledger's guarantees live in database constraints and triggers, so use a managed database with backups. |
| **Redis** | Version 7, `maxmemory-policy noeviction`, persistence on | BullMQ queues. Evicting keys loses jobs. |

By default one process serves the API **and** runs the workers, which is enough to start. To scale, see [Separate API and worker instances](#separate-api-and-worker-instances).

Database migrations run as a separate step before the new version starts:

```bash
node node_modules/typeorm/cli.js migration:run -d dist/database/data-source.js
```

Migrations are safe to re-run: applied ones are skipped.

## Option 1: Render, in one click

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/Fabulouscode/finstack)

The button reads [`render.yaml`](../render.yaml) and creates, in your Render account:

- `finstack-db`: PostgreSQL 17
- `finstack-redis`: Key Value (Redis-compatible), with `noeviction`, private to your account
- `finstack-api`: the API and its workers. Migrations run on every deploy, before the app starts.

It deploys a **sandbox** (`SANDBOX_MODE=true`): production settings, but with the mock provider and `fsk_test_` API keys, so no real money can move. Secrets (`JWT_ACCESS_SECRET`, `DATA_ENCRYPTION_KEY`, `METRICS_TOKEN`, `MOCK_PROVIDER_WEBHOOK_SECRET`) are generated by Render; you never type them.

**Steps**

1. Click the button and sign in to Render.
2. Review the services and click **Apply**. The first build takes a few minutes.
3. When `finstack-api` is live, open `https://<your-service>.onrender.com/health/ready`. It should report the database and Redis as `up`.
4. Open `https://<your-service>.onrender.com/docs` for the interactive API docs.
5. Register a user, then [make yourself an admin](#the-first-admin).

**Free plans are for trying FinStack only.** Render's free database expires after 30 days, free Key Value keeps no data across restarts, and free web services sleep when idle (the first request after a pause is slow). For anything real, switch all three to paid plans. On a paid web service, also move the migration into a pre-deploy command, so a failing migration never receives traffic:

- **Pre-deploy command:** `node node_modules/typeorm/cli.js migration:run -d dist/database/data-source.js`
- **Docker command:** `node dist/main.js`

## Option 2: Any Docker host

Use this for Railway, Fly.io, AWS ECS, Google Cloud Run, a VPS, or Kubernetes.

**1. Provide PostgreSQL 17 and Redis 7.** Managed services are recommended. Configure Redis with `maxmemory-policy noeviction` and persistence (AOF or snapshots).

**2. Build and push the image.**

```bash
docker build -t registry.example.com/finstack:0.1.1 .
docker push registry.example.com/finstack:0.1.1
```

**3. Set the configuration** from [Production configuration](#production-configuration), as environment variables or secrets in your platform.

**4. Run migrations** as a one-off job with the same image and configuration:

```bash
docker run --rm --env-file production.env registry.example.com/finstack:0.1.1 \
  node node_modules/typeorm/cli.js migration:run -d dist/database/data-source.js
```

**5. Start the app.**

```bash
docker run -d --env-file production.env -p 3000:3000 registry.example.com/finstack:0.1.1
```

If your platform has no separate job step, start the container with `sh docker/start.sh` instead. It runs the migrations, then the app.

**6. Point your load balancer's health checks** at:

- `GET /health/live`: the process is up (use for restarts)
- `GET /health/ready`: the database and Redis are reachable (use for routing traffic)

`docker-compose.yml` in the repository shows the same pieces wired together locally, including the one-shot `migrate` service.

## Production configuration

`.env.example` documents every setting. FinStack validates its configuration at startup and **refuses to start** with unsafe production settings (for example a test payment key, the public development encryption key, or the mock provider outside a sandbox), and it names each problem in the log.

### Required

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME` | Your PostgreSQL connection |
| `DATABASE_SSL` | `true` when connecting over a public network; private networks may not need it |
| `REDIS_HOST`, `REDIS_PORT` (and `REDIS_PASSWORD` if set) | Your Redis connection |
| `JWT_ACCESS_SECRET` | At least 32 random characters: `openssl rand -base64 48` |
| `DATA_ENCRYPTION_KEY` | Exactly 32 random bytes, base64: `openssl rand -base64 32`. Encrypts secrets FinStack must read back, such as webhook signing secrets. **Back it up**: losing it makes those secrets unreadable. |

### Recommended

| Variable | Why |
|---|---|
| `TRUST_PROXY_HOPS` | The number of proxies in front of the app (usually `1`), so audit logs and rate limits see the real client IP |
| `CORS_ORIGINS` | Your dashboard's origin, if a browser calls the API directly |
| `METRICS_TOKEN` | Enables `/metrics` for Prometheus; without it, metrics are off in production |
| `EMAIL_DRIVER=smtp`, `EMAIL_FROM`, `SMTP_URL` | Sends notification emails (otherwise they are only logged) |
| `SWAGGER_ENABLED` | Off by default in production. Turn it on for a sandbox, keep it off for live. |

### Payments

| Variable | Value |
|---|---|
| `PAYMENT_PROVIDERS` | For example `paystack,stripe`. `mock` is refused in production unless `SANDBOX_MODE=true`. |
| `DEFAULT_PAYMENT_PROVIDER` | The provider used when no other rule picks one |
| `PAYMENT_CURRENCY_ROUTES` | Optional fixed routing, for example `NGN:paystack,USD:stripe`. Without it, FinStack suggests a provider per currency and clients may choose. |
| `PAYSTACK_SECRET_KEY` | `sk_live_...` (live) or `sk_test_...` (sandbox) |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | From the Stripe dashboard (see [Provider webhooks](#provider-webhooks)) |
| `STRIPE_SUCCESS_URL`, `STRIPE_CANCEL_URL` | Where Stripe Checkout returns the customer |
| `FLUTTERWAVE_SECRET_KEY`, `FLUTTERWAVE_WEBHOOK_SECRET_HASH`, `FLUTTERWAVE_REDIRECT_URL` | From the Flutterwave dashboard (see [Provider webhooks](#provider-webhooks)) |
| `MOCK_PROVIDER_WEBHOOK_SECRET` | Sandbox only: signs simulated provider webhooks |

## Going live

A sandbox and a live deployment use the same image. Going live is a configuration change, but take it one step at a time.

**1. Use a separate deployment.** Keep the sandbox running for development and give live its own database, Redis and secrets. Never point a sandbox at live data.

**2. Switch off the sandbox.**

```bash
SANDBOX_MODE=false
SWAGGER_ENABLED=false
PAYMENT_PROVIDERS=paystack,stripe      # no mock
DEFAULT_PAYMENT_PROVIDER=paystack
```

**3. Add live provider keys** (`sk_live_...`). FinStack refuses test keys in a live deployment, and live keys in a sandbox.

**4. Register the provider webhooks** (below) and send one small real payment before opening the doors.

**5. Turn on the risk controls you need:**

| Setting | Suggested start |
|---|---|
| `PAYOUT_DESTINATION_COOLDOWN_MINUTES` | `1440`: a new bank account can receive payouts after 24 hours, and the owner is emailed when one is added |
| `PAYMENT_SETTLEMENT_DELAY_SECONDS` | For example `172800` (2 days): payments sit in the pending balance before they can be spent or paid out |
| Fee and limit rules | Created through the admin API (see the README) |

**6. Check the operations basics:** database backups (and a tested restore), a backup of `DATA_ENCRYPTION_KEY`, log collection, alerts on `/health/ready`, and a person who reads the daily reconciliation results.

**7. Check the legal side.** Holding customer funds, converting currencies and paying out can be regulated activities. Make sure your business is licensed or partnered for what you enable.

### Provider webhooks

Providers must reach FinStack over public HTTPS.

| Provider | URL | Setup |
|---|---|---|
| Paystack | `https://<your-domain>/v1/webhooks/paystack` | Dashboard → Settings → API Keys & Webhooks. Paystack signs with your secret key; there is no separate webhook secret. For payouts, turn off transfer OTP (Settings → Preferences) and add a business phone number on the compliance page. |
| Stripe | `https://<your-domain>/v1/webhooks/stripe` | Dashboard → Developers → Webhooks → Add endpoint. Copy the signing secret (`whsec_...`) into `STRIPE_WEBHOOK_SECRET`. |
| Flutterwave | `https://<your-domain>/v1/webhooks/flutterwave` | Dashboard → Settings → Webhooks. Set a long random **secret hash** and put the same value in `FLUTTERWAVE_WEBHOOK_SECRET_HASH`; Flutterwave sends it in the `verif-hash` header. |

Events to enable in Stripe:

- `checkout.session.completed`
- `checkout.session.async_payment_succeeded`
- `checkout.session.async_payment_failed`
- `checkout.session.expired`
- `refund.created`, `refund.updated`, `refund.failed`

FinStack verifies every signature, stores each event once, and re-checks the payment with the provider before moving money. Duplicate and late webhooks are safe.

### The first admin

There is no default admin account. Register through the API, then promote that user in the database:

```sql
UPDATE users SET role = 'admin' WHERE email = 'you@example.com';
```

Sign in again so the new access token carries the role. From then on, staff roles are assigned through the API (`POST /v1/admin/users/:id/role`), with every change audited.

## Operating FinStack

### Releasing a new version

1. Build and push the new image.
2. Run migrations with the **new** image.
3. Roll out the new image.

During a rolling deploy the old version briefly runs against the new schema. Adding tables, columns and constraints is safe. If a migration removes or renames something the old version still uses, release in two steps: first stop using it, then remove it in the next release.

### Separate API and worker instances

When traffic grows, split the roles so a burst of background work never slows the API:

| Instance | Setting | Count |
|---|---|---|
| API | `WORKERS_ENABLED=false` | As many as traffic needs |
| Worker | `WORKERS_ENABLED=true` | One or more |

On Render, add a **Background Worker** service with the same image and environment, and set `WORKERS_ENABLED=false` on the web service.

### Monitoring

- **Health:** `/health/live` and `/health/ready`
- **Logs:** JSON in production, with request and trace ids on every line
- **Metrics:** `GET /metrics` with `Authorization: Bearer $METRICS_TOKEN`
- **Daily reconciliation** runs at 02:00 UTC. Open items are listed at `GET /v1/admin/reconciliation/items`.
- **Failed webhooks** can be inspected and replayed through the admin API.
